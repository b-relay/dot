# Architecture: Interactive Dotfiles Setup Wizard

**Research Date:** 2026-01-27
**Domain:** Dotfiles management with interactive setup
**Confidence:** HIGH (verified with official chezmoi docs, multiple tool implementations)

## Executive Summary

Interactive dotfiles setup wizards follow a **three-phase architecture**: detect system state, guide user through adaptive questions, then generate and apply configurations. The key insight from tools like chezmoi is separating **source state** (templates + data), **target state** (generated configs), and **actual state** (what's on disk), enabling intelligent change detection and idempotent operations.

For bidirectional sync (template→config AND config→dotfiles), the pattern is **extract + merge with validation checkpoints** rather than true real-time sync, using file watching to trigger extraction and timestamped backups before merging.

## Component Architecture

### 1. State Detector

**Purpose:** Discover what's already on the system before asking questions

**Responsibilities:**
- Detect installed tools and their versions (`which`, `--version` parsing)
- Identify existing shell configuration (oh-my-zsh, zinit, vanilla zsh)
- Scan for existing dotfiles in `~` and `~/.config`
- Check architecture (ARM vs Intel) and platform details
- Detect active Git configuration (user, email, signing keys)
- Inventory Homebrew packages

**Outputs:** `SystemState` object with:
```typescript
{
  shell: { type: 'zsh' | 'bash', manager: 'oh-my-zsh' | 'zinit' | null },
  installedTools: Map<string, { version: string, path: string }>,
  architecture: 'arm64' | 'x86_64',
  existingDotfiles: Array<{ path: string, type: 'file' | 'symlink' | 'dir' }>,
  gitConfig: { user?: string, email?: string, signingKey?: boolean },
  homebrewPackages: Array<string>
}
```

**Implementation Pattern:**
- Run detection in parallel where possible (tool checks are independent)
- Use `.nothrow().quiet()` for command failures (absence is data)
- Cache detection results for the session (don't re-detect)

**Build Order:** Build FIRST (everything depends on this)

### 2. Wizard Engine

**Purpose:** Guide user through adaptive questions based on detected state

**Responsibilities:**
- Present questions conditionally (only ask what's relevant)
- Validate user input and provide helpful defaults
- Store answers in structured data model
- Skip questions when detection provides answers
- Handle multi-step flows with progress indication

**Architecture Pattern:** **State machine** with conditional transitions

```
State Machine Example:
┌─────────────┐
│ Welcome     │
└──────┬──────┘
       │
       v
┌─────────────┐     ┌──────────────────┐
│ Shell Setup │────>│ Plugin Selection │ (if new setup)
└──────┬──────┘     └──────────────────┘
       │
       v
┌─────────────┐     ┌──────────────────┐
│ Git Config  │────>│ Create SSH Keys  │ (if missing)
└──────┬──────┘     └──────────────────┘
       │
       v
┌─────────────┐
│ Confirm     │
└─────────────┘
```

**Conditional Logic Examples:**
- IF oh-my-zsh detected → ask "Keep oh-my-zsh or migrate to zinit?"
- IF no oh-my-zsh → ask "Install oh-my-zsh, zinit, or minimal setup?"
- IF Git user.name exists → skip, use detected value
- IF no SSH key → offer to generate one

**Data Model:**
```typescript
{
  shell: {
    manager: 'oh-my-zsh' | 'zinit' | 'minimal',
    plugins: string[],
    theme: string
  },
  git: {
    name: string,
    email: string,
    generateSSHKey: boolean,
    enableSigning: boolean
  },
  tools: {
    starship: boolean,
    rust: boolean,
    fnm: boolean,
    bun: boolean,
    tmux: boolean
  }
}
```

**Library Choice:** **@inquirer/prompts** (modern, ESM-compatible, type-safe) or **enquirer** (faster, lighter)

**Build Order:** Build SECOND (after detector, before templater)

---

### 3. Template Engine

**Purpose:** Generate configuration files from templates using wizard data

**Responsibilities:**
- Render templates with user choices + detected state
- Support conditionals (IF/ELSE), loops, and variables
- Handle architecture-specific paths (Homebrew location)
- Generate multiple files from single template set
- Validate generated output (syntax checking)

**Template Pattern:** **Go-style templates** (like chezmoi) or **Handlebars-style**

**Example Template (zshrc):**
```bash
# Generated by dot setup wizard
# Architecture: {{architecture}}

{{#if tools.starship}}
eval "$(starship init zsh)"
{{/if}}

{{#if shell.manager == 'oh-my-zsh'}}
export ZSH="$HOME/.oh-my-zsh"
plugins=({{#each shell.plugins}}{{this}} {{/each}})
source $ZSH/oh-my-zsh.sh
{{/if}}

{{#if tools.fnm}}
eval "$(fnm env --use-on-cd)"
{{/if}}

# Homebrew path for {{architecture}}
{{#if architecture == 'arm64'}}
export PATH="/opt/homebrew/bin:$PATH"
{{else}}
export PATH="/usr/local/bin:$PATH"
{{/if}}
```

**Template Variables:**
- `.detected.*` - Everything from SystemState
- `.user.*` - Everything from wizard answers
- `.meta.*` - Generation metadata (timestamp, version)

**Storage:**
- Templates live in `templates/` directory
- Naming: `zshrc.hbs`, `gitconfig.hbs`, etc. (`.hbs` = template)
- Shared snippets in `templates/_includes/`

**Build Order:** Build THIRD (after wizard)

---

### 4. Config Migrator

**Purpose:** Move existing configs into dotfiles structure (backup + symlink)

**Responsibilities:**
- Backup existing config files before changes
- Copy configs to dotfiles repo structure
- Create symlinks from original locations to dotfiles
- Handle conflicts (file exists vs symlink exists)
- Track migration state (what's been migrated)

**Migration Flow:**
```
1. Detect existing config at ~/.gitconfig
2. Create backup at ~/.dotfiles/backups/gitconfig.20260127-143052
3. Copy to ~/.dotfiles/git/.gitconfig
4. Remove original ~/.gitconfig
5. Symlink ~/.config/git/config -> ~/.dotfiles/git/.gitconfig
6. Record in migration log
```

**Conflict Resolution:**
- If symlink exists and points correctly → skip
- If symlink exists but wrong target → warn, ask user
- If regular file exists → backup, replace with symlink
- If neither exists → just create symlink

**Backup Strategy:**
- Timestamped backups: `original-name.YYYYMMDD-HHMMSS`
- Store in `.dotfiles/backups/` (gitignored)
- Keep last 5 backups per file, auto-prune older

**Build Order:** Build FOURTH (after templater, runs during setup)

---

### 5. Bidirectional Sync Engine

**Purpose:** Backport changes from installed configs back to dotfiles/templates

**Responsibilities:**
- Watch installed config files for changes
- Extract changed content
- Determine if change should update template or just dotfile
- Merge changes back with validation
- Create backups before merging

**Architecture Pattern:** **Extract + Merge with Validation**

**Two Sync Directions:**

**A. Config → Dotfiles (Simple)**
```
User edits ~/.config/git/config
  ↓
File watcher detects change
  ↓
Copy updated file to ~/.dotfiles/git/.gitconfig
  ↓
Show git diff, prompt to commit
```

**B. Config → Template (Complex - requires human decision)**
```
User edits ~/.zshrc
  ↓
File watcher detects change
  ↓
Show diff between current and last generated
  ↓
Ask: "Update template or just dotfile?"
  ↓ (if template)
Extract variable portions vs literal
  ↓
Update template with new literals
  ↓
Test regeneration produces correct output
```

**Implementation Details:**
- File watching via **launchd** (macOS native, ~2-5MB vs fswatch ~10-20MB)
- Throttle: 5-second delay to avoid rapid cascading triggers
- Validation: Parse config format (JSON, TOML, etc.) before merging
- Backups: Timestamped before every merge
- Dry-run mode: Show what would change without applying

**Challenge:** Distinguishing template variables from literal changes
- **Heuristic:** If new content looks like template variable syntax → warn
- **Solution:** Mark template regions with comments for guidance
- **Fallback:** Only update dotfile, flag for manual template update

**Build Order:** Build FIFTH (advanced feature, can defer to later milestone)

### 6. Symlink Manager (Existing)

**Purpose:** Install/uninstall symlinks based on LINKS map

**Note:** This already exists in current codebase (`install()`, `uninstall()`)

**Enhancement Needed:**
- Decouple from hardcoded LINKS map
- Use config file or generated LINKS from wizard
- Support per-tool installation (install just Git config, not everything)

**Build Order:** REFACTOR during migration (extract into module)

## Data Flow

### Setup Flow (Fresh Machine)

```
1. Run: dot setup
   ↓
2. STATE DETECTOR scans system
   ↓
3. WIZARD ENGINE asks conditional questions
   ↓
4. TEMPLATE ENGINE generates configs
   ↓
5. CONFIG MIGRATOR creates backups, symlinks
   ↓
6. SYMLINK MANAGER installs links
   ↓
7. Verify installation, show next steps
```

### Migration Flow (Existing Dotfiles)

```
1. Run: dot setup --migrate
   ↓
2. STATE DETECTOR finds existing configs
   ↓
3. WIZARD asks: "Found .gitconfig, migrate to dotfiles?"
   ↓
4. CONFIG MIGRATOR:
   - Backup existing files
   - Copy to dotfiles structure
   - Create symlinks
   ↓
5. TEMPLATE ENGINE generates missing configs
   ↓
6. Show git diff, prompt to commit
```

### Sync Flow (Backport Changes)

```
User edits ~/.zshrc
   ↓
File watcher (launchd) detects change after 5s
   ↓
SYNC ENGINE extracts changes
   ↓
Validate syntax (zsh -n)
   ↓
Backup before merge
   ↓
Copy to ~/.dotfiles/zsh/zshrc
   ↓
Prompt: git diff, commit?
```

## Component Boundaries

### Clear Separation of Concerns

| Component | Reads From | Writes To | Depends On |
|-----------|------------|-----------|------------|
| State Detector | Filesystem, shell commands | Memory (SystemState) | None |
| Wizard Engine | SystemState, user input | Memory (WizardData) | State Detector |
| Template Engine | Templates, WizardData, SystemState | Generated files (memory) | Wizard, Detector |
| Config Migrator | Filesystem, generated files | Dotfiles repo, backups, symlinks | Template Engine |
| Sync Engine | Filesystem (watch), dotfiles repo | Dotfiles repo, backups | Config Migrator |
| Symlink Manager | Config file (LINKS map) | Filesystem (symlinks) | None |

### Module Structure

```
dot/
├── src/
│   ├── detector/
│   │   ├── system.ts        # Main detection orchestrator
│   │   ├── tools.ts         # Tool detection (which, version parsing)

│   │   └── dotfiles.ts      # Existing dotfile scanning
│   ├── wizard/
│   │   ├── engine.ts        # State machine + question flow
│   │   ├── questions/       # Question definitions by domain
│   │   │   ├── shell.ts
│   │   │   ├── git.ts
```

## Key Architectural Patterns from Research

### 1. Three-State Model (from chezmoi)

> **Source State** (templates + data) → evaluate → **Target State** (generated configs) → compare → **Actual State** (filesystem)

This enables:
- Idempotent operations (safe to re-run)
- Change detection (only update what changed)
- Dry-run mode (show diff without applying)

**Application to dot:**
- Source = templates + wizard data
- Target = rendered configs (in memory or temp dir)
- Actual = current filesystem state
- Compare before writing, show diffs

### 2. System Abstraction Layer (from chezmoi)

Rather than direct filesystem operations everywhere, route through abstraction:
- `RealSystem` - actual filesystem ops
- `DryRunSystem` - read-only, log writes
- `TestSystem` - in-memory for tests

**Application to dot:**
```typescript
interface System {
  readFile(path: string): Promise<string>
  writeFile(path: string, content: string): Promise<void>
  symlink(target: string, path: string): Promise<void>
  exists(path: string): Promise<boolean>
}
```

Benefits:
- Easy testing (inject TestSystem)
- Safe dry-run mode (inject DryRunSystem)
- Single place to add logging/debugging

### 3. Config File Template for Init (from chezmoi)

When user runs `dot init`, look for `.dot.config.toml.tmpl`:
- If exists, render it with prompts
- Store rendered config for future runs
- Use config to customize all subsequent operations

**Application to dot:**
- Bootstrap: `dot init` asks minimal questions, generates `.dot/config.toml`
- Setup: `dot setup` uses existing config or creates if missing
- Modify: `dot config edit` re-runs wizard to update choices

### 4. Prompt Once Pattern (from chezmoi)

```typescript
// Don't re-prompt if already answered
const email = config.git?.email || await promptString("Git email?")
```

Store answers in config file, only prompt for missing values. Enables:
- Partial setup (answer some questions, defer others)
- Re-running setup without annoyance
- Updating single setting without full wizard

### 5. Alternate File Pattern (from yadm)

Instead of templates with conditionals, use filename suffixes:
- `.zshrc##` - default
- `.zshrc##Darwin` - macOS only
- `.zshrc##Darwin.arm64` - Apple Silicon only

**Application to dot:**
Could complement templates for simpler cases:
- `gitconfig##work` vs `gitconfig##personal`
- `brewfile##minimal` vs `brewfile##full`

But templates are more flexible for complex cases.

### 6. Extract + Merge Pattern (from MCP config sync)

For bidirectional sync:
1. **Extract:** Pull specific section from large file
2. **Validate:** Check JSON/TOML syntax with `jq` or parser
3. **Backup:** Timestamped backup before any merge
4. **Merge:** Reintegrate with conflict detection
5. **Verify:** Test that merged config loads correctly

**Application to dot:**
```bash
# Extract git config from ~/.gitconfig (if merged with other stuff)
$ dot sync extract git

# Backup current dotfiles version
$ dot sync backup ~/.dotfiles/git/.gitconfig

# Merge changes back
$ dot sync merge git

# Verify it parses correctly
$ git config --list --file ~/.dotfiles/git/.gitconfig
```

### 7. State Machine for Complex Wizards (from xstate-wizards)

For wizards with many conditionals, use formal state machine:

```typescript
const wizardMachine = createMachine({
  initial: 'welcome',
  states: {
    welcome: {
      on: { NEXT: 'detectShell' }
    },
    detectShell: {
      invoke: {
        src: 'detectShellService',
        onDone: {
          target: 'shellQuestions',
          actions: 'saveDetection'
        }
      }
    },
    shellQuestions: {
      on: {
        HAS_OH_MY_ZSH: 'askMigrate',
        NO_MANAGER: 'askInstallManager'
      }
    },
    askMigrate: {
      on: {
        MIGRATE: 'gitQuestions',
        KEEP: 'gitQuestions'
      }
    }
    // ... more states
  }
})
```

Benefits:
- Clear visualization of flow
- Impossible to reach invalid states
- Easy to add new paths
- Testable transitions

**For dot:** Consider for future if wizard gets very complex, but probably overkill for initial version. Start with simple conditional logic, refactor to state machine if needed.

## Anti-Patterns to Avoid

### 1. Monolithic Setup Function
**Bad:** One giant `setup()` function that does everything
**Good:** Separate detector, wizard, templater, migrator phases

### 2. Inline Templates
**Bad:** Template strings in TypeScript code
**Good:** Templates in separate files, loaded at runtime

### 3. No Validation
**Bad:** Write generated configs directly to filesystem
**Good:** Parse and validate syntax before writing

### 4. Destructive Operations Without Backup
**Bad:** Overwrite existing configs immediately
**Good:** Always backup before modifying, keep last N backups

### 5. Re-prompting Answered Questions
**Bad:** Ask same questions every time wizard runs
**Good:** Store answers in config, prompt once

### 6. Hardcoded Paths
**Bad:** Assume `/opt/homebrew` or specific username
**Good:** Detect architecture, use `$HOME`, make portable

### 7. No Dry-Run Mode
**Bad:** Only way to test is to run for real
**Good:** `--dry-run` flag shows what would happen

### 8. Silent Failures
**Bad:** Try to create symlink, silently skip if fails
**Good:** Detect conflicts, report clearly, offer resolution

## Scalability & Extension

### Adding New Tool Configuration

To add support for a new tool (e.g., Neovim):

1. **State Detector:** Add detection logic
```typescript
// src/detector/tools.ts
export async function detectNeovim(): Promise<ToolInfo | null> {
  const exists = await isToolInstalled('nvim')
  if (!exists) return null
  const version = await getVersion('nvim', '--version')
  return { name: 'neovim', version, path: await which('nvim') }
}
```

2. **Wizard:** Add questions
```typescript
// src/wizard/questions/tools.ts
export const neovimQuestions = (detected: SystemState) => [
  {
    type: 'confirm',
    name: 'tools.neovim',
    message: 'Configure Neovim?',
    default: detected.tools.has('neovim')
  }
]
```

3. **Template:** Add template file
```lua
-- templates/nvim/init.lua
-- Generated by dot setup wizard

vim.opt.number = true
vim.opt.relativenumber = true

{{#if user.tools.neovim.language == 'rust'}}
-- Rust-specific config
require('rust-tools').setup({})
{{/if}}
```

4. **Migrator:** Add to LINKS map
```typescript
if (wizardData.tools.neovim) {
  links[`${dotfiles}/nvim/init.lua`] = `${dotconfig}/nvim/init.lua`
}
```

No changes needed to core architecture!

## Open Questions & Research Gaps

### 1. Template Language Choice
**Options:**
- Handlebars (familiar, good ecosystem)
- Mustache (simpler, widely supported)
- Custom (full TypeScript, max flexibility)

**Recommendation:** Start with **Handlebars**, it's well-documented and has good TypeScript support. Can switch later if needed.

### 2. Config Storage Format
**Options:**
- TOML (chezmoi uses this, good for config)
- JSON (simple, native parsing)
- YAML (readable, but strict indentation)

**Recommendation:** **TOML** for human editing, matches chezmoi patterns users might know.

### 3. File Watching Approach
**Options:**
- launchd (macOS native, lightweight)
- fswatch (cross-platform, heavier)
- chokidar (Node library, good for dev)
- Manual: `dot sync` command (no watching)

**Recommendation:** Start with **manual sync command**, add launchd watching in later milestone. Keeps initial scope manageable.

### 4. Handling Secrets
**Pattern:** Store in dotfiles folder but gitignore
```
.dotfiles/
  secrets/
    ssh_key_personal      # gitignored
    ssh_key_work         # gitignored
    .gitignore           # ignore secrets/
```

Wizard generates keys, stores in `secrets/`, creates symlinks to proper locations (`~/.ssh/`).

### 5. Multi-Machine Profiles
**Question:** Same person, different machines (work vs personal laptop)?

**Pattern from chezmoi:**
```toml
[data]
  hostname = "work-macbook"
  profile = "work"

[data.git]
  email = "user@company.com"  # work profile
```

Templates can use `{{#if profile == 'work'}}` conditionals.

**For dot:** Add "profile" concept in wizard, store in config, use in templates.
